# Архитектура и границы ответственности

[English](../en/architecture.md) | [Русский](../../README.ru.md)

## За что отвечает ReMgu

```text
исследовательский вопрос
          ↓
   гипотеза + мотивация
          ↓
         Run ───────────────┐
          │                 │
          ├─ run.yaml       ├─ жизненный цикл исполнения
          ├─ params.yaml    ├─ фактическая конфигурация
          ├─ metrics.csv    ├─ история метрик
          └─ samples.jsonl  └─ компактные диагностические примеры
          ↓
      вывод + следующий шаг
```

ReMgu добавляет небольшой слой хранения и управления жизненным циклом поверх существующего Python-эксперимента. Он не отвечает за обучение модели, загрузку данных, расчёт метрик, поиск гиперпараметров, планирование задач или удалённый tracking-сервис.

## Основные компоненты

- `Experiment` — фасад для создания запуска или повторного открытия активного запуска из training code.
- `Run` — конкретное исполнение; фиксирует переходы состояния и записывает артефакты.
- `Motivation`, `ResearchMetadata`, `Execution`, `Review` — структурированные части записи запуска.
- `FileStorage` — хранение метаданных и указателя активного запуска в файловой системе.
- `TopKSelector` / `ExampleSelector` — отбор диагностических примеров с ограниченным использованием памяти.
- `ExampleProvider` — протокол для получения исходного примера по его ID средствами конкретного проекта.
- `check_consistency` — read-only проверка сохранённых исследовательских записей.
- `research.cli` — CLI над теми же файловыми данными.

## Архитектурные границы

**Код эксперимента → ReMgu.** Проект отвечает за обучение, оценку, датасеты и предметные метрики. ReMgu сохраняет гипотезу, снимок конфигурации, поток метрик и выбранные диагностические примеры.

**ReMgu → файловая система.** Текущая реализация хранит обычные YAML, CSV, JSONL и небольшой текстовый указатель. База данных или сервер не нужны.

**Проверка согласованности → сохранённые файлы.** Проверка читает исходные записи, чтобы сообщать о некорректных данных. Она не меняет записи и не исправляет их автоматически.

**Будущие слои знаний/агентов → ReMgu.** В будущем база знаний или агент смогут создавать гипотезы и анализировать результаты, но не должны быть жёстко встроены в ядро жизненного цикла. В текущей версии эти слои не реализованы.

## Зачем отдельно хранить исполнение и разбор

Процесс может завершиться успешно, но не подтвердить гипотезу. Поэтому `execution.status = completed` не означает, что `review.status = reviewed`. Вывод исследователя и следующий шаг записываются отдельным этапом.

## Текущие ограничения

- Хранение локальное и файловое; параллельные писатели и распределённое исполнение не координируются.
- Один каталог исследований поддерживает один активный запуск.
- ReMgu не рассчитывает метрики и не проверяет их научный смысл.
- `samples.jsonl` не является хранилищем датасета и сам не разрешает ID в исходные данные.
- Проверка согласованности выявляет структурные проблемы и нарушения workflow, но не исправляет их.
- Публикация, база знаний, оркестрация агентов и генерация сайта — будущие направления, а не текущие функции.
