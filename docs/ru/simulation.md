# API симулятора: контролируемые эксперименты с графовой зависимостью

Пакет симуляции предоставляет небольшую среду без новых обязательных зависимостей для проверки гипотез о структуре графа и доступности информации. Это не фреймворк обучения моделей; результаты на синтетических данных не гарантируют перенос на production.

## Сценарий: несёт ли критический мост целевой сигнал?

### Мотивация и гипотеза

Пусть метка целевой вершины зависит от признака, находящегося в другом сообществе графа. Если сообщества соединены единственным мостом, его удаление должно сделать исходный признак недостижимым. Сравним один и тот же граф с фиксированным seed до и после вмешательства.

Гипотеза для конкретного запуска не подтверждается, если мост удалён, но его концы остаются связными, либо если измеренное поведение модели не соответствует ожидаемой зависимости. Accuracy — измеряемый результат, а не гарантия: если исходный признак соответствует отрицательному классу, предсказание по умолчанию может остаться правильным и после разрыва связи.

### Запуск через Python API

```python
from remgu import (
    CriticalBridgeCheck,
    RemoveEdgeOperator,
    SimulationConfig,
    SimulationExperiment,
    SimulationRunner,
    PredictionAccuracyCheck,
)

config = SimulationConfig(
    experiment_id="critical-bridge",
    hypothesis="Удаление единственного моста делает положительный удалённый сигнал недоступным.",
    seed=4,
    community_sizes=(5, 5),
    edge_probability=0.0,
)
runner = SimulationRunner(checks=[PredictionAccuracyCheck(), CriticalBridgeCheck()])
experiment = SimulationExperiment(config, runner)

baseline = experiment.run()
intervened = experiment.run([RemoveEdgeOperator((4, 5))])
print(baseline.metrics)
print(intervened.metrics)
print(intervened.checks)
```

Генератор обеспечивает связность внутри каждого сообщества цепочкой, добавляет внутренние рёбра с вероятностью `edge_probability` и соединяет сообщества заданным мостом. По умолчанию источник сигнала — последняя вершина, а целевые вершины находятся в другом сообществе. В примере ребро `(4, 5)` соответствует размерам сообществ `(5, 5)`.

### Ожидаемый результат и интерпретация

Для указанного seed признак источника положительный. В baseline источник достижим из всех целевых вершин, accuracy равна 1.0. После удаления ребра `(4, 5)` целевые вершины не могут достичь источника, baseline выдаёт предсказание по умолчанию, и accuracy падает до 0.0. Проверка критического моста сообщает, что его концы разъединены.

`CriticalBridgeCheck` проверяет только связность графа: остались ли соединёнными концы указанного моста. Сам по себе он не измеряет accuracy и не доказывает, что обученная модель не использует обходные признаки. Accuracy отдельно проверяет `PredictionAccuracyCheck`. Чтобы проверить возможное использование обходных признаков, добавьте отдельную проверку, сравнивающую поведение модели до и после вмешательства.

Точные числа зависят от seed и конфигурации. Для контролируемого сравнения используйте одну и ту же конфигурацию и seed; иначе изменения графа и признаков могут смешаться с эффектом вмешательства.

### Операторы графа и преобразования данных

Графовые операторы возвращают новый мир и не изменяют входной объект. `AddIsolatedNodesOperator` позволяет проверять, что добавление несущественных изолированных вершин не меняет метки исходных вершин. `RemoveEdgeOperator` может удалить заданный мост, сохранив метаданные о том, какое ребро было критическим.

`TransformPipeline` поддерживает преобразование конечного датасета и ленивое преобразование батчей по мере поступления. Режим `batch` обрабатывает и выдаёт по одному батчу, не материализуя весь поток. Источник случайности передаётся явно, чтобы обеспечить воспроизводимость.

```python
from remgu import NumericNoiseTransform, RandomSource, TransformPipeline

pipeline = TransformPipeline([NumericNoiseTransform("feature", 0.05)], mode="batch")
batches = pipeline.transform_batches(training_batches, RandomSource(seed=21))
for batch in batches:
    train_step(batch)  # существующий код обучения
```

Замените `training_batches` и `train_step` своим загрузчиком данных и шагом обучения. Само обучение ReMgu не реализует.

### Сохранение результата в существующем research-запуске

```python
from remgu import Experiment, Motivation, ResearchRunAdapter

research_experiment = Experiment("graph-study")
with research_experiment.run(
    "Критический мост управляет доступом к удалённому признаку",
    Motivation(type="new"),
) as run:
    ResearchRunAdapter().record(run, intervened)
```

Адаптер сохраняет конфигурацию и статус в параметрах запуска, метрики — в `metrics.csv`, а краткую сводку — в `samples.jsonl`. Он не создаёт и не завершает запуск и не меняет существующую схему `.research`.

## Диагностика и ограничения

- `Probe` вызывает необязательный метод адаптера `get_probe_data()`. Если метода нет или он возвращает `None`, результат явно указывает, что диагностика недоступна. Градиенты и активации автоматически не выводятся.
- `ModelIntervener` поддерживает явную временную замену существующего атрибута с записью для восстановления. Это не универсальный механизм вмешательства в нейросети.
- Включённый baseline — простое правило достижимости, а не бенчмарк современных GNN или Mamba-архитектур.
- CLI симулятора, браузерный UI и live-дашборд доступны; они остаются лёгкими необязательными компонентами. GPU-профилирование зависит от `remgu[monitor]`; спектральный генератор графов не входит в текущую версию.


- Отчёты и визуализация доступны без обязательной установки ML-фреймворков. Дашборд по умолчанию доступен только на локальном компьютере. Если ресурс или схема модели не могут быть измерены или построены, ReMgu явно показывает, что данных нет; встроенная визуализация архитектуры поддерживает не все варианты синтаксиса Graphviz DOT.

## Отчёт и дашборд: что выбрать

### 1. Проверить гипотезу и сохранить результат

```bash
research simulation run --seed 7 --nodes-per-community 8 --output result.json
research simulation report result.json --output report.html
```

Первая команда проводит эксперимент с заданным seed и сохраняет результат. Вторая создаёт HTML-отчёт, который можно открыть в браузере или отправить коллеге. Фиксированный seed помогает сравнивать эксперименты, не смешивая эффект вмешательства со случайными изменениями данных.

### 2. Посмотреть сохранённый результат в браузере

```bash
research simulation dashboard result.json --port 8765
```

Откройте локальный адрес, напечатанный командой. На странице есть графики метрик, сведения о доступных ресурсах, выбранные примеры и визуальные представления графа или архитектуры модели, если данные доступны. Эта команда показывает сохранённый `result.json`; сама по себе она не подключается к процессу обучения.

### 3. Наблюдать за своим обучением

Самый короткий вариант — обернуть функцию обучения декоратором. ReMgu запускает локальный дашборд, периодически измеряет доступные ресурсы и гарантированно останавливает сервер после завершения функции.

```python
from remgu import DashboardServer

dashboard = DashboardServer()

@dashboard.track()
def train():
    print("Dashboard URL:", dashboard.url)
    for epoch in range(num_epochs):
        train_one_epoch()
        dashboard.log_metrics(loss=loss, accuracy=validation_accuracy)

train()
```

`train_one_epoch`, `loss` и `validation_accuracy` здесь — переменные и функции вашего проекта. Единственный вызов, нужный для отправки метрик, — `log_metrics(...)`; вручную создавать `ResourceMonitor`, собирать словарь состояния и вызывать `update_state()` не требуется. Альтернатива с контекстным менеджером: `with dashboard.run(): ...`; внутри блока сервер и мониторинг активны, после выхода они останавливаются. Чтобы показывать метрики без `log_metrics`, передайте в `run()` или `track()` параметр `metrics` — функцию без аргументов, возвращающую словарь текущих значений.

### Что означают элементы страницы

- **График метрик** показывает, как меняются loss, accuracy и другие числовые значения по мере обучения. Для loss обычно ожидают снижение; для accuracy — рост, но оценивайте их вместе и на корректной выборке.
- **CPU и RAM** показывают нагрузку процесса, если система позволяет её измерить. GPU и видеопамять появляются, если доступны соответствующие драйверы и библиотеки. Недоступное измерение показывается как отсутствующее, а не как ноль.
- **Отобранные примеры** помогают увидеть, на каких данных модель ошибается или ведёт себя необычно.
- **Ползунок параметра** позволяет менять только те параметры, которые автор эксперимента специально подключил к управлению во время обучения. Это может быть, например, learning rate; изменение ползунка не меняет произвольную переменную Python автоматически. Параметры, для изменения которых нужно пересоздать модель или оптимизатор, помечаются как требующие перезапуска.
- **Логи** показывают сообщения и диагностические события, которые публикует обучение.

### Отбор примеров: доступные стратегии

`ExampleSelectionService` умеет отбирать: `random` — случайную выборку; `top_k` — записи с наибольшим значением поля `score` (или другого `score_key`); `errors` — ошибочные предсказания; `confident_errors` — ошибочные предсказания, отсортированные по уверенности модели от большей к меньшей; `correct_predictions` — правильные предсказания; `hard` — примеры с наибольшим `difficulty`; `rare_examples` — примеры с наименьшей частотой `frequency`; `has_bridge` — записи, помеченные `has_bridge=True`.

Например, `confidence=0.93` означает 93% уверенности. Стратегия `confident_errors` **не задаёт порог 90%**: она ранжирует ошибочные примеры по уверенности, поэтому ошибки с уверенностью 0.93 появятся раньше ошибок с 0.4. Для `correct_predictions` требуется поле `correct`; для `confident_errors` — `correct` и `confidence`; для `hard` — `difficulty`; для `rare_examples` — числовое `frequency`; для `has_bridge` — `has_bridge`. Если необходимых полей нет, ReMgu сообщает об этом явно.

### Установка мониторинга CPU/RAM/GPU

```bash
pip install "remgu[monitor]"
```

Это необязательная установка: остальные функции отчёта и дашборда работают и без неё. Набор доступных показателей зависит от операционной системы, драйверов и установленных библиотек. Дашборд по умолчанию доступен только на вашем компьютере.

### Дополнительные инструменты для Python

```python
from remgu import StaticHtmlReport, GraphRenderer, MetricRenderer

report_path = StaticHtmlReport().render(result, "report.html", events=probe_events)
dot_text = GraphRenderer().to_dot(world)
metric_svg = MetricRenderer().render({"validation_accuracy": [0.61, 0.72, 0.79]})
```

`StaticHtmlReport` создаёт автономный отчёт, `GraphRenderer` возвращает описание графа, а `MetricRenderer` строит SVG-график из готовой истории метрик. Эти инструменты визуализируют переданные данные, но не запускают обучение и не вычисляют метрики за пользователя.

### Схема архитектуры модели

```python
from remgu import ArchitectureAdapter, DotSvgRenderer

dot = ArchitectureAdapter().get_architecture_dot(model)
if dot is not None:
    svg = DotSvgRenderer().render(dot)
```

Если модель или её фреймворк не поддерживаются либо не предоставляют достаточно сведений, результатом будет `None`. Адаптеры для PyTorch, Keras, CatBoost, spaCy и Word2Vec используют уже доступные в объекте метаданные; они не устанавливают и не импортируют тяжёлые ML-фреймворки автоматически. Полученная схема — обзорная визуализация, а не гарантия полного отображения всех внутренних вычислений модели.

## Типы миров и визуализаторы

`GraphWorld` — первая реализованная среда симуляции, но не обязательное условие для обычных экспериментов ReMgu. Он реализует общий контракт `SimulationWorld`: проверку данных, независимое копирование, представление в виде словаря, краткое описание и читаемый текстовый вид. `WorldRenderer` умеет показывать любой мир с таким контрактом; `GraphRenderer` дополнительно строит SVG и DOT для графов. В будущем текстовый мир или мир с синтетическими историями просмотров пользователей сможет реализовать те же общие методы и добавить собственный визуализатор и операторы. Текущий `SimulationRunner` и графовые операторы пока рассчитаны на графы.
